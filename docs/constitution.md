# momoflow의 기본 사상

## 목적

사람이 매 작업을 감독하는 대신 목표와 경계를 정하면, 에이전트가 개발과 개선을
주도한다. momoflow 자체가 첫 번째 개선 대상이다. 제품의 기능뿐 아니라 개발 방식도
작은 실행과 검증을 통해 개선한다.

## 역할 경계

사용자와 대화하는 보조자는 목표·우선순위·결과를 함께 논의한다. 기능 개발을 먼저
수행하지 않으며, 재귀 개선이 멈추거나 시스템이 정상 작동하지 않을 때 재개에 필요한
최소한의 조치만 한다. 사용자가 명시적으로 요청한 문서 정리 등은 해당 요청 범위에서
수행할 수 있다. 실제 기능 개발과 개선은 루프 안의 실행 에이전트가 주도한다.
초기에는 사용자가 시점을 정한 배포와 실패 복구도 보조자가 운영 절차로 수행할 수 있다.
배포 자동화 구현은 개발 에이전트의 일이며, 준비 조건이 충족되면 일반 변경의 배포까지
루프에 포함한다. 상세 기준은 [배포 운영과 자동화](deployment.md)에 둔다.

## 개발 원칙

1. **MVP first.** 현재 목표를 만족하는 가장 작은 동작을 먼저 완성한다.
2. **증거 기반 개선.** 실행 결과, 테스트 실패, 리뷰 지적, 실제 사용의 불편에서 다음 일을 찾는다.
3. **에이전트 주도.** 범위 안의 설계·구현·검증·수정은 에이전트가 결정한다.
4. **필요한 사람 개입.** 권한 부족, 제품 방향의 모호함, 스스로 해결할 수 없는 장애에만 개입을 요청한다.
5. **작은 재귀.** 구현 → 검증 → 리뷰 → 수정의 반복으로 목표를 달성한다. 활동량을 성과로 삼지 않는다.
6. **점진적 엔진 소유.** Symphony를 실제 엔진으로 시작하고, 필요가 입증된 기능부터 하나씩 흡수한다.
7. **정책의 분리.** 개선 중인 에이전트가 자기 평가 기준, 권한, 예산을 스스로 완화하지 않는다.

## 재귀 개선의 두 단계

현재 부트스트랩은 한 목표 안에서 최대 세 번 구현·검증·리뷰를 반복하는 루프다.
목표를 만족하면 종료하고, 발견한 후속 개선은 근거와 완료 조건을 가진 이슈로 남긴다.
일반적인 구현 단계마다 사람의 승인을 받지 않는다.

다음 단계는 후속 개선의 선택과 실행까지 이어지는 목표 간 루프다. 이를 활성화하려면
지속적으로 저장되는 실행 예산, 중복 목표 방지, 자동 승격 조건, 회귀 판정이 먼저 필요하다.
그 기능이 없는 현재에는 후속 이슈에 실행 라벨을 자동으로 붙이지 않는다. 따라서 현재
구성을 무제한 자기개선 시스템이나 완성된 자율 개발 플랫폼으로 표현하지 않는다.

## 완료와 반영

완료는 코드 변경뿐 아니라 실제 검증 결과와 리뷰 근거를 포함한다. 적용 가능한 저장소
규칙과 CI 조건을 만족하는 변경은 에이전트가 자율적으로 반영할 수 있다. 규칙을 우회하지
않으며, 요구되는 사람의 리뷰가 있다면 그 리뷰가 필요한 시점만 대기한다.

작업 결과는 PR 등 영속적인 위치에 보존한다. 실행 성공만으로 이슈를 닫거나 작업 공간을
삭제하지 않는다. 실행 중인 자기 자신의 엔진을 바로 교체하지 않으며, 엔진·정책 변경은
다음 버전의 검증된 배포로 적용한다.

개선은 일반적인 GitHub의 Issue → PR → CI·리뷰 → 병합 흐름을 따른다.
첫 목표는 작은 이슈 하나를 단계별 사람 개입 없이 검증·병합까지 완료하는 것이다.
그다음 후속 목표 선택과 실행을 연결한다. 근거 있는 다음 개선이 없으면 종료하며,
계속 실행하기 위해 일을 만들어내지 않는다. 구체적인 운영 합의와 현재 구현의 차이는
[GitHub 개선 흐름](github-flow.md)에 기록한다.

## 초기 예산의 한계

WORKFLOW.md의 세 번 반복 제한은 에이전트가 따르는 정책이다. Symphony의 max_turns는
개별 실행 세션의 턴 제한이고, 재시도와 후속 이슈 전체의 비용 한도가 아니다. 하드 예산
제어는 별도 개선 항목이며, 현재 보장되는 기능으로 표시하지 않는다.
