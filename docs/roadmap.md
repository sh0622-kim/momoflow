# 작은 단계로 만드는 momoflow

각 단계는 이전 단계에서 관찰한 문제와 하나의 검증 가능한 완료 조건을 가진다.
아래 순서는 방향이며 모든 기능을 미리 구현하라는 지시가 아니다.
운영 흐름의 합의는 [GitHub 개선 흐름](github-flow.md)에 있다.

| 단계 | 가장 작은 결과 | 완료 기준 |
| --- | --- | --- |
| 0. 부트스트랩 | Docker + Symphony 기반 엔진 + Codex + 기본 웹 대시보드 | 이미지 빌드, 엔진 기동, 실제 한 이슈 실행 검증 |
| 1. 첫 자기개선 | 작은 이슈 하나를 PR·CI·리뷰·병합까지 완료 | 단계별 사람 개입 없이 병합된 변경과 검증 근거; 실제 필요한 대기·재개 연결부터 보완 |
| 1a. 배포 절차 검증 | 사용자가 정한 시점에 검증된 버전으로 교체 | 정확한 이미지·설정 식별, 신규 작업 접수 차단, 작업 보존, 기동 확인과 복구 기록 |
| 1b. 배포 수행 자동화 | 수동 시작 한 번으로 배포·실패 복구 수행 | 연속 배포 성공 두 번 및 격리된 실패 복구 검증 한 번 |
| 2. 실행 이력과 예산 | 목표별 반복 횟수와 결과를 영속적으로 기록 | 재시작 후에도 예산을 초과한 작업이 재실행되지 않음 |
| 3. 목표 간 개선 | 근거 있는 후속 목표 하나를 자동 승격 | 중복 방지와 예산 소진 중단을 자동 테스트로 검증 |
| 3a. 운영까지 자기개선 | 조건을 만족한 병합을 작업 종료 경계에서 자동 배포 | 병합 → 배포 → 운영 확인 → 후속 판단 연결, 실패 시 자동 복구; 일반 변경의 단계별 사람 개입 없음 |
| 4. momoflow 웹 UI | 목표, 실행 결과, 개입이 필요한 이유 표시 | Symphony의 실제 상태와 화면이 일치 |
| 5. 기능 흡수 | 관찰된 제약 하나를 해결하는 자체 구현 | 기존 엔진과의 계약 테스트 및 되돌리기 경로 확보 |

초기에는 별도 DB, 큐 서버, 자체 스케줄러를 두지 않는다. GitHub Issues가 작업의 원본이고,
Symphony가 실행 상태를 소유한다. 영속적인 개선 이력이 필요해지는 2단계에서 저장 방식을
결정한다. 팀 확장은 실제 다중 사용자 요구가 생겼을 때 인증과 권한 모델부터 검토한다.
배포 자동화는 필수 후속 목표다. [배포 정책](deployment.md)의 조건이 충족되면 전환하며,
숫자 순서 때문에 이미 준비된 자동화를 미루거나 자체 UI·엔진 재작성을 선행 조건으로 삼지 않는다.

## 부트스트랩에서 수행한 첫 개선

제목: `Symphony 엔진 기동 스모크 검사를 자동화한다`

- 관찰: Docker 이미지가 빌드되어도 대시보드와 상태 API가 실제로 동작하는지 별도 확인이 필요하다.
- 범위: 가짜 트래커 자격 증명, 네트워크 차단, 빈 작업 공간으로 로컬 기동만 검증한다.
- 완료 조건: 대시보드와 `/api/v1/state`가 응답하고, 종료 후 테스트 컨테이너가 남지 않는다.
- 제외: 실제 Codex 호출, GitHub 변경, 신규 서비스나 테스트 프레임워크 추가.
- 구현: `scripts/smoke.sh`. Docker 빌드 후 실행해 상태 API와 대시보드를 확인한다.

이 개선은 현재 개발 세션의 검토에서 발견해 구현했다. Symphony가 이슈를 가져와 수행한
자기개선 실행은 아직 아니다. 실제 엔진을 통한 첫 작업은 인증 연결 후 작게 선택한다.

사용자의 명시적 요청으로 GitHub App 연결까지 대화 보조자의 부트스트랩 범위에 포함했다.
봇 인증 기준선은 키 격리, 설치 토큰 갱신, Symphony의 작은 토큰 파일 패치로 구성한다.
운영·검증 방법은 [README](../README.md)에 둔다. 이 작업도 엔진이 수행한 자기개선으로 세지 않는다.

## 다음 작은 개선 후보

역할별 순차 실행을 [에이전트 실행 정책](agent-policy.md)에 맞춰 구현한다. 기획·검토는
Astra, 구현·수정은 Sol을 사용하며 실제 설정·세션 근거와 Fast OFF를 확인한다.
첫 구현은 정책의 단일 에이전트 부트스트랩 조건을 먼저 충족한 뒤 시작한다.

첫 PR 흐름에 필요한 사람 개입 라벨과 GitHub 액션 연결을 구현한다. 승인·수정 요청·직접
병합·닫기부터 작게 시작하고, 댓글 결정은 요청 식별자와 작성자 구분이 준비된 다음 연결한다.
[개입 처리 계약](human-actions.md)의 현재 head·중복 이벤트·자기 승인 방지 조건을 검증한다.

빌드에서 보고된 upstream 의존성 보안 권고를 조사하고, 영향이 확인된 패키지 하나의
최소 업데이트를 검증한다. 전체 엔진 교체보다 먼저 해당 변경의 빌드·기동·회귀 근거를 남긴다.

스모크 검사의 실패 원인을 구분해 표시한다. 현재는 기동 실패, API 형식 오류, 대시보드
오류를 마지막 컨테이너 로그로 진단한다. 각 실패의 원인을 출력하고, 의도적으로 잘못된
이미지나 설정을 사용했을 때 원인이 표시되는 것을 완료 조건으로 삼는다. 신규 서비스나
테스트 프레임워크는 추가하지 않는다.

아직 실제 에이전트 실행을 시작하지 않았다. 부트스트랩 운영 기록은 개발 에이전트의
실행 결과와 구분하며, 첫 개발 이슈의 실행 라벨은 별도로 선택해 부여한다.
